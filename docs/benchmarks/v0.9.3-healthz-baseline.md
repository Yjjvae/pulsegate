# v0.9.3 `/healthz` 多 Worker 基线

## 目标

测量当前 Release 网关在本机回环 `/healthz` 上随 `io_context` worker 数变化的吞吐和尾延迟。
这是一项**基线和并发模型对照实验**，不代表 TLS、反向代理、磁盘、日志或真实网络部署的性能。

## 拓扑与负载

- 服务：`build/release/app/pulsegate --config <generated-config>`；
- 地址：`127.0.0.1:18082`；
- 路径：`GET /healthz`，固定短响应；
- 每组只改变 `server.io_threads`：1、2、4、8；
- `wrk -t2 -c100 -d15s --latency`；每组先预热 5 秒，再独立运行 3 次；
- 生成的 YAML 将 `logging.level` 设为 `critical`，因此 access log 不会成为这项网络/调度基线的瓶颈；
- `ulimit -n` 为 1,048,576，`somaxconn` 为 4096；每份 wrk 输出未出现 socket error 或 non-2xx 行。

## 复现

```bash
cmake --preset release
cmake --build --preset release

tools/benchmark.sh --workers 1,2,4,8 --trials 3 \
  --connections 100 --load-threads 2 --warmup 5s --duration 15s
```

脚本将原始 `wrk` 输出、生成配置和环境元数据写入 `benchmarks/results/<timestamp>/`。该目录被忽略，
因此应将环境、原始命令和汇总结果写入像本文这样的版本化报告。若 `wrk` 不在 `PATH`，可设置
`WRK_BIN=/path/to/wrk`。

## 结果

| I/O worker | RPS（3 次原始值） | 中位 RPS | P99（3 次原始值） | 中位 P99 | 峰值 RSS | 峰值 CPU |
| ---------: | --- | ---: | --- | --- | ---: | ---: |
| 1 | 81,948.69 / 89,733.83 / 75,321.21 | 81,948.69 | 2.64 / 2.29 / 2.31 ms | 2.31 ms | 6,772 KiB | 99.9% |
| 2 | 174,675.97 / 176,944.97 / 181,780.37 | 176,944.97 | 1.13 / 1.05 / 1.00 ms | 1.05 ms | 6,892 KiB | 198.0% |
| 4 | 309,868.85 / 311,430.35 / 305,056.09 | **309,868.85** | 463 / 459 / 481 µs | **463 µs** | 7,052 KiB | 359.0% |
| 8 | 255,737.02 / 255,336.30 / 253,555.82 | 255,336.30 | 573 / 601 / 578 µs | 578 µs | 7,568 KiB | 567.0% |

CPU 是测量期每秒采样的进程生命周期平均 `%CPU` 的最大值；RSS 同样按秒采样。因此它们用于量级判断，
而不是替代专用 profiler。

4 worker 相比 1 worker 的中位吞吐约提升 278%，且 P99 从 2.31 ms 降至 463 µs。8 worker 较 4 worker
下降约 18%，同时 RSS 和 CPU 占用更高，说明此轻量回环负载已更受同机 `wrk`、调度和共享状态开销影响，
而非缺少更多 worker。

## Profile 与优化决策

本 WSL2 环境没有与 `6.18.33.2-microsoft-standard-WSL2` 匹配的 `perf` 可执行程序，故没有伪造
flame graph 或热点结论。Asio handler tracking 也未启用：它是 Debug 诊断功能，会显著扰动本项 Release
测量。

本轮**未修改网关热路径**。理由是没有 profile 证据表明 Buffer、HTTP parser、日志、指标、缓存或
连接池中的哪一个是瓶颈；仅凭 8 worker 的回落不足以证明某个实现缺陷。当前可复现的结论是：此环境下
`--threads 4` 是 `/healthz` 基线的最佳实验点。默认 worker 数保持不变，因为真实代理、缓存和容器负载
可能有不同最优值。

下一次性能 PR 必须给出 profile 证据、预期改善的指标、风险、相同矩阵的 before/after 数据，以及在
改善低于测量噪声时的回退结论。

## 局限与后续实验

- 服务端与压测端同机，无法代表真实网络；
- 只测试短小本地响应；后续应单独测 proxy、cache hit/miss、慢上游和不同响应大小；
- 连接数固定为 100；应在独立实验中覆盖 1、10、100、500、1000；
- 在原生 Linux 或匹配 perf 工具的环境中采集 `perf record -F 99 -g`，再决定是否优化；
- 不将本报告的绝对 RPS 写成跨版本或跨机器的性能承诺。
