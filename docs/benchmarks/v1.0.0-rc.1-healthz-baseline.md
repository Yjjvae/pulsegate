# v1.0.0-rc.1 `/healthz` 候选基线

## 目标与范围

本报告记录 `v1.0.0-rc.1` 候选 commit 在本机 loopback `GET /healthz` 上的吞吐和尾延迟，用作发布前可复现的并发模型基线。它不代表 TLS、反向代理、磁盘、日志、真实网络或生产硬件的性能承诺。

- 服务端与压测端均在同一 WSL2 主机，使用 `127.0.0.1:18082`；
- 每组只改变 `server.io_threads`：1、2、4、8；
- `wrk -t2 -c100 -d15s --latency`，每次测量前预热 5 秒；
- YAML 将 `logging.level` 设为 `critical`，避免访问日志成为测试瓶颈；
- 每份原始输出均未报告 socket error 或 non-2xx 响应。

原始数据位于被 Git 忽略的 `benchmarks/results/v1.0.0-rc.1-matrix/`。由于受控命令会话的时长限制，12 次测量按 worker/trial 独立启动服务；因此这是同参数的三次独立运行，而不是让同一服务进程连续承载三次负载。该差异及同机竞争会放大低 worker 数的噪声。

## 结果

| I/O worker | RPS（3 次原始值） | 中位 RPS | P99（3 次原始值） | 中位 P99 | 峰值 RSS | 峰值 CPU |
| ---------: | --- | ---: | --- | --- | ---: | ---: |
| 1 | 50,796.22 / 45,275.62 / 99,082.18 | 50,796.22 | 3.10 / 3.40 / 1.92 ms | 3.10 ms | 6,760 KiB | 99.8% |
| 2 | 174,054.37 / 175,466.87 / 173,430.29 | 174,054.37 | 0.97 / 0.97 / 0.98 ms | 0.97 ms | 6,952 KiB | 198.0% |
| 4 | 306,454.31 / 307,053.43 / 306,994.42 | **306,994.42** | 432 / 432 / 425 µs | **432 µs** | 7,056 KiB | 359.0% |
| 8 | 254,754.34 / 249,914.02 / 247,728.32 | 249,914.02 | 544 / 550 / 562 µs | 550 µs | 7,392 KiB | 565.0% |

CPU 和 RSS 由测试期按秒采样的进程生命周期平均值取峰值，只用于量级判断。4 worker 的结果稳定且为此测试的最佳点；8 worker 吞吐下降约 19%，同时 CPU/RSS 更高。worker=1 的 RPS 波动显著，不能据此声称回归或改善。

与 [v0.9.3 基线](v0.9.3-healthz-baseline.md) 相比，2、4、8 worker 的中位结果仍处于相近量级；但测试是在不同时间的同机 WSL2 环境中进行，不能做精确的跨版本百分比结论。

## 复现与结论

在非受限宿主终端中，使用连续的标准矩阵：

```bash
cmake --preset release
cmake --build --preset release

tools/benchmark.sh --workers 1,2,4,8 --trials 3 \
  --connections 100 --load-threads 2 --warmup 5s --duration 15s
```

本候选未据此修改网关热路径。现有证据支持把 4 worker 作为这个轻量 loopback 实验的最佳点；真实代理、容器、缓存、慢上游和 TLS 负载仍需要独立实验与 profile 证据。
