# v0.4.0 `io_context` Worker 对照实验

## 目的

只改变 `pulsegate --threads N`，比较单个 `io_context` 由不同数量 worker 执行时的
`/healthz` 回环基线。该实验验证第十章并发模型，不代表通用生产吞吐量。

## 固定条件

- 使用 Release 可执行程序；
- 回环地址 `127.0.0.1`；
- `wrk -t2 -c100 -d15s --latency`；
- 每轮前确认没有残留 PulseGate 进程；
- 记录 CPU、内存、内核、编译器和 Boost 版本。

## 运行命令

```bash
./build/release/app/pulsegate --listen 127.0.0.1:18082 --threads <N>
wrk -t2 -c100 -d15s --latency http://127.0.0.1:18082/healthz
```

## 结果

| I/O worker | 连接数 | RPS | P99 | 错误 |
| ---------: | -----: | --: | --: | ---: |
|          1 |    100 | 121,216.78 | 1.57 ms | 0 |
|          2 |    100 | 238,339.27 | 812 µs | 0 |
|          4 |    100 | 311,228.23 | 437 µs | 0 |
|          8 |    100 | 259,467.59 | 570 µs | 0 |

环境：Ubuntu 26.04 WSL2（Linux `6.18.33.2-microsoft-standard-WSL2`），AMD Ryzen 7
8845H（16 逻辑 CPU），GCC 15.2.0、CMake 4.2.3、Boost 1.90.0、wrk 4.1.0。

每轮服务启动后先用 `curl --noproxy '*' --include` 确认 `HTTP/1.1 200 OK` 和 `ok\n`，
随后运行 15 秒 wrk；没有 socket error 或非 2xx 错误。

## 解读规则

worker 数不会线性提高 RPS。应同时检查：CPU 物理核/SMT、同一个 `io_context` 的调度开销、
共享状态锁竞争、负载生成器是否饱和，以及是否把所有 Session 错误地放进了全局 strand。

本次 4 worker 最好；8 worker 反而下降，说明本机的轻量 `/healthz` 负载已经受到调度和
负载生成器竞争影响。这个结果不应外推到包含上游 I/O、TLS、日志或 CPU 业务的服务。
